# 开源项目调研与技术借鉴

## 1 调研目的

本调研服务于课程项目的技术选型，不以复制某个大型量化框架为目标。判断标准依次为：是否直接支持单因子研究、是否适合沪深 A 股、能否私有部署、学习和集成成本、许可证风险，以及是否有利于展示“平台与产品”的边界。

调研日期：2026年10月10日。正式引用代码前仍须核对所使用版本的许可证文件。

## 2 候选项目比较

| 项目 | 适合参考的内容 | 不直接采用的原因 | 本项目决策 |
| --- | --- | --- | --- |
| [Microsoft Qlib](https://github.com/microsoft/qlib) | 数据集、因子/信号、工作流、实验记录、分析结果之间的分层；配置驱动和代码驱动两种研究入口 | 覆盖机器学习、强化学习、组合与执行，远超课程首期范围；整体接入会显著提高学习成本 | **主要架构参考，不作为首期运行时依赖** |
| [Alphalens](https://github.com/quantopian/alphalens) | 前向收益、分位数组、IC、换手率、分组分析和 tear sheet 的经典口径 | 原仓库年代较早，直接依赖可能遇到现代 Pandas 兼容问题；也不提供用户、数据版本和任务平台 | **指标定义与黄金结果参考** |
| [QUANTAXIS](https://github.com/yutiansut/QUANTAXIS) | 国内市场语境下的数据、因子、异步计算、消息队列、任务调度和 Web 服务模块划分 | 同时覆盖行情、回测、交易、账户、分布式等大量功能，技术栈和部署面过重 | **模块边界与 A 股字段参考** |
| [RQAlpha](https://github.com/ricequant/rqalpha) | A 股交易日历、撮合、费用、涨跌停以及可插拔 Mod 机制 | 核心是策略回测与交易，不是因子研发；仓库说明为非商业使用，不能不加判断地复制代码 | **P1 回测口径参考，P0 不依赖** |
| [vectorbt](https://github.com/polakowo/vectorbt) | 向量化组合模拟、参数扫描和交互图表 | 当前项目首先要证明因子有效性而不是构建高速交易回测；社区版还包含 Commons Clause 限制 | **仅作为 P1 性能与组合模拟参考** |
| [MLflow Tracking](https://github.com/mlflow/mlflow) | Run/Experiment、参数、指标、代码版本和 artifact 的追踪模型 | 整体引入会增加一个服务和重复 UI；首期记录字段很少，自建足够 | **借鉴数据模型，暂不引入服务** |
| [DuckDB](https://duckdb.org/docs/current/data/parquet/overview) | 直接查询 Parquet、列裁剪和过滤下推，适合本地离线分析 | 不负责业务事务、账号权限和任务状态 | **保留为行情与因子矩阵查询引擎** |

## 3 最值得吸收的设计

### 3.1 采用 Qlib 式分层，但缩减为四层

1. **数据层**：数据集版本、证券范围、字段字典、质量结果和 Parquet 文件。
2. **因子层**：因子定义、参数、版本和标准化后的因子矩阵。
3. **研究工作流层**：实验参数、执行任务、日志、状态和复现信息。
4. **分析展示层**：指标、图表数据和 HTML 报告。

四层之间只传递明确的数据对象，前端不直接操作研究计算模块。Qlib 本身强调松耦合组件和完整研究工作流，这一原则适合本项目；机器学习模型库、强化学习和在线服务不进入首期。

### 3.2 采用 Alphalens 式单因子输入契约

研究引擎统一接收以下长表：

| 字段 | 含义 |
| --- | --- |
| `trade_date` | 因子形成日 |
| `symbol` | 证券代码 |
| `factor_value` | 当日因子值 |
| `forward_return_1d` | 下一交易日收益 |
| `industry` | 可选，行业中性化与分组统计使用 |
| `market_cap` | 可选，市值中性化使用 |

Alphalens 明确要求因子值与 forward returns 对齐，并提醒信号形成时点必须避免前视偏差。本项目继续坚持“收盘后形成的 t 日因子最早对应 t+1 收益”。

### 3.3 采用 MLflow 式实验记录

每次研究运行不可变地保存：

- `experiment_id` 与 `run_id`；
- 数据集版本和因子版本；
- 全部处理参数；
- 代码版本；
- 开始时间、结束时间、状态和错误摘要；
- 指标 JSON、图表数据、日志和报告等 artifacts。

首期由本项目自己的 PostgreSQL 表和文件目录实现，不部署 MLflow。若后续加入机器学习模型，再评估直接接入 MLflow。

### 3.4 保留模块化单体与独立 Worker

QUANTAXIS 的完整架构包含因子、异步计算、消息系统、调度和 Web 服务，证明这些边界在大型系统中确实存在；但课程项目不需要复制其微服务和分布式规模。首期仍采用 FastAPI 模块化单体、Celery Worker、PostgreSQL、Redis、Parquet 和 DuckDB。

## 4 不应照搬的设计

- 不引入 Qlib 的机器学习训练、强化学习、在线服务和订单执行。
- 不把 Alphalens 直接当作系统平台；它只解决因子分析，不解决数据治理、权限与任务。
- 不建设 QUANTAXIS 级别的实时行情、账户、消息总线和分布式 Agent。
- 不在 P0 接入 RQAlpha 或 vectorbt；课程验收没有交易撮合要求。
- 不为了“像开源项目”而增加微服务、Kubernetes、MongoDB、ClickHouse 或 MLflow Server。
- 不复制许可证不清晰或限制性项目的源码；需要的公式依据公开定义独立实现，并用测试验证。

## 5 对当前代码的直接影响

当前工程方向基本正确，无须推翻：React + FastAPI 负责产品与平台入口，Worker 负责计算，PostgreSQL 保存元数据，Parquet + DuckDB 保存和查询大表。

后续实现顺序调整为：

1. 先建立 `DatasetVersion`、`FactorVersion`、`Experiment`、`Run`、`Artifact` 五个核心实体。
2. 把目前进程内任务替换为可持久化的 Run 状态机。
3. 将研究引擎输入统一为 Alphalens 风格长表契约。
4. 逐项补齐 IC、Rank IC、ICIR、分组收益、换手率，并用独立黄金数据测试。
5. 在 P0 完成后才评估 RQAlpha/vectorbt 的简单多因子组合回测。

## 6 结论

本项目应采取“**Qlib 的流程骨架 + Alphalens 的指标口径 + MLflow 的实验记录模型 + DuckDB 的本地数据查询**”，而不是直接二次开发某个完整量化系统。这样既能证明调研基础，也能保持课程项目可讲解、可验收和按期完成。
